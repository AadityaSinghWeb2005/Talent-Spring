1. PROJECT OBJECTIVE
================================================================================
The primary objective is to architect and build a production-grade, highly reliable, 
scalable, and secure Full-Stack Job Portal Application. 

The application serves three distinct user roles:
1. Candidate / Job Seeker: Profile building, resume management, job search, filter, 
   bookmarking, one-click apply, application tracking, notifications, interview scheduling.
2. Employer / Recruiter: Company management, job posting lifecycle (draft, active, paused, 
   closed), applicant candidate tracking system (ATS), stage transitions, interview 
   scheduling, candidate evaluation notes, hiring analytics.
3. System Administrator: User/Company/Job moderation, platform role assignments, 
   reported job/content review, platform analytics, audit logging, system settings.

Non-functional Objectives:
- SLA: 99.9% uptime.
- Performance: Sub-100ms API p95 response time; sub-2s initial page rendering.
- Security: Zero OWASP Top 10 vulnerabilities, strict RBAC, encrypted PII.
- Scalability: Up to 100,000 active users without architectural rewrites.

2. FIRST PRINCIPLE & TECHNOLOGY DECISION MATRIX
================================================================================
Every technology in this project is selected based on zero-trust evaluation of project 
requirements rather than industry trends.

--------------------------------------------------------------------------------
Technology Choice 1: Monolithic Node.js / TypeScript Backend vs Microservices
--------------------------------------------------------------------------------
- Decision: Modular Monolith (TypeScript + Express/Fastify).
- Rationale: Microservices introduce network latency, distributed transaction complexity 
  (Saga pattern), deployment overhead, and premature optimization for early-stage portals.
- Justification over alternatives: A modular monolith allows logical boundaries between 
  domains (Auth, Job, Application, Notification) within a single deployment unit, enforcing 
  strict layer separation while preserving ACID database transactions across domains.

--------------------------------------------------------------------------------
Technology Choice 2: PostgreSQL vs MongoDB / NoSQL
--------------------------------------------------------------------------------
- Decision: PostgreSQL 16+.
- Rationale: Job portals are inherently relational and data-integrity critical. Applications 
  belong to Candidates and Jobs; Jobs belong to Companies; Companies contain Recruiters. 
  Foreign key constraints, CASCADE actions, atomic state transitions, and ACID properties 
  prevent orphan records and duplicate applications.
- Justification over alternatives: MongoDB lacks built-in declarative schema constraints across 
  collections, making duplicate applications or orphaned resumes common without heavy 
  application-level locking.

--------------------------------------------------------------------------------
Technology Choice 3: PostgreSQL Full-Text Search (TSVector) vs Elasticsearch
--------------------------------------------------------------------------------
- Decision: PostgreSQL Built-in Full-Text Search (TSVector + GIN Index) for initial launch.
- Rationale: Adding Elasticsearch introduces cluster management, sync lag, data 
  reconciliation scripts, and extra hosting costs. PostgreSQL `tsvector` with `pg_trgm` 
  handles tens of thousands of jobs and fuzzy skill queries with sub-20ms response time.
- Justification over alternatives: Decouples infrastructure overhead until job volume exceeds 
  500,000 active listings.

--------------------------------------------------------------------------------
Technology Choice 4: Next.js (App Router) vs Vite + SPA
--------------------------------------------------------------------------------
- Decision: Next.js 14+ (App Router) with SSR & Server Components.
- Rationale: Job postings require aggressive Search Engine Optimization (SEO), OpenGraph 
  meta tags for social sharing, and fast Server-Side Rendering (SSR) for web crawlers (Google 
  Jobs indexer).
- Justification over alternatives: Single Page Applications (Vite) render client-side, 
  severely hindering SEO discoverability for open job positions.

11. NORMALIZATION & DENORMALIZATION STRATEGY
================================================================================
- Normalization (3NF Guarantee): All core tables strictly satisfy 3NF. Entities like skills, 
  status histories, and companies are thoroughly normalized into dedicated tables to ensure zero 
  update/delete anomalies.
- Selective Denormalization:
  1. `jobs.search_vector`: Pre-computed `TSVECTOR` updated via database trigger to eliminate 
     costly runtime string concatenations during search queries.
  2. `jobs.views_count`: Atomically incremented integer on job detail fetch.

================================================================================
12. DATABASE INDEXING STRATEGY
================================================================================
Indexes are defined based on strict query profile patterns:

1. Job Search & Filtering Index:
   `CREATE INDEX idx_jobs_search_composite ON jobs(status, workplace_type, experience_level, created_at DESC) WHERE status = 'ACTIVE';`
   WHY THIS INDEX EXISTS: Prevents full table scans when filtering open job listings on 
   the landing and job search pages.

2. Full-Text Search Index:
   `CREATE INDEX idx_jobs_search_vector ON jobs USING GIN(search_vector);`
   WHY THIS INDEX EXISTS: Enables sub-20ms weighted lexical and title keyword search.

3. Unique Candidate Application Constraint Index:
   `CREATE UNIQUE INDEX idx_unique_candidate_job_app ON applications(job_id, candidate_id);`
   WHY THIS INDEX EXISTS: Enforces at the database engine level that a candidate can only apply 
   once to a specific job listing, eliminating application-level race conditions.

4. Foreign Key Lookup Indexes:
   `CREATE INDEX idx_applications_candidate ON applications(candidate_id);`
   `CREATE INDEX idx_applications_job ON applications(job_id);`
   `CREATE INDEX idx_company_members_user ON company_members(user_id);`

13. SQL QUERY ARCHITECTURE
================================================================================
PostgreSQL Trigger for Full-Text Search Vector Sync:
```sql
CREATE OR REPLACE FUNCTION jobs_search_vector_trigger() RETURNS trigger AS $$
BEGIN
  NEW.search_vector :=
    setweight(to_tsvector('english', coalesce(NEW.title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(NEW.description, '')), 'B');
  RETURN NEW;
END
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_jobs_search_vector_update
BEFORE INSERT OR UPDATE ON jobs
FOR EACH ROW EXECUTE FUNCTION jobs_search_vector_trigger();

```

Faceted Job Search Query with Pagination (Cursor-based):

```sql
SELECT 
  j.id, j.title, j.location_city, j.salary_min, j.salary_max, j.created_at,
  c.name AS company_name, c.logo_url
FROM jobs j
JOIN companies c ON j.company_id = c.id
WHERE j.status = 'ACTIVE'
  AND j.search_vector @@ plainto_tsquery('english', $1)
  AND ($2::VARCHAR IS NULL OR j.workplace_type = $2)
  AND ($3::NUMERIC IS NULL OR j.max_salary >= $3)
  AND j.created_at < $4
ORDER BY j.created_at DESC
LIMIT $5;

```

14. TRANSACTIONS & ACID ISOLATION

Multi-step transactional operations MUST run within explicit database transactions with appropriate isolation levels.

Example Transaction: Application Submission

```sql
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 1. Check job availability and lock row
SELECT id, status FROM jobs WHERE id = $1 FOR SHARE;

-- 2. Insert application (Fails if duplicate due to UNIQUE constraint)
INSERT INTO applications (id, job_id, candidate_id, resume_id, current_status)
VALUES ($2, $1, $3, $4, 'APPLIED');

-- 3. Log initial status history
INSERT INTO application_status_history (id, application_id, changed_by_user_id, from_status, to_status)
VALUES ($5, $2, $3, NULL, 'APPLIED');

COMMIT;

```

15. CONCURRENCY CONTROL & RACE CONDITIONS

1. Double-Application Prevention: Managed by `UNIQUE (job_id, candidate_id)` database index constraint.
2. Concurrent Status Change: Optimistic concurrency control using `updated_at` timestamps or row locking using `SELECT ... FOR UPDATE`.
3. Application to Closed Jobs: Checked within transactional read lock (`FOR SHARE`).

# ================================================================================
16. PAGINATION STRATEGY

* Admin Dashboard / User Lists: Offset-based pagination (`LIMIT x OFFSET y`). Suitable for deep jumping pages where total count is required.
* Candidate Job Search Feed / Recruiter Applicant Feed: Cursor-based keyset pagination (`WHERE created_at < $last_seen_timestamp ORDER BY created_at DESC LIMIT n`). Eliminates query performance degradation on deep pages and prevents missing/duplicate items when new records are added concurrently.

17. SEARCH SYSTEM ARCHITECTURE

The job search pipeline uses PostgreSQL native TSVector with `pg_trgm` extension for fuzzy matching.

* Search Targets: Job title (weight 'A'), Job description (weight 'B'), Company name, and required Skill taxonomy.
* Ranking Function: `ts_rank_cd(search_vector, query)` combined with date decay parameters.

# ================================================================================
18. AUTHENTICATION ARCHITECTURE

* Password Hashing: Argon2id with standard OWASP parameters (Memory: 64MB, Parallelism: 2, Iterations: 3).
* Token Management: Dual JWT pattern.
* Access Token: Short-lived (15 minutes), payload contains `{ userId, roles, companyId }`.
* Refresh Token: Long-lived (7 days), stored in HTTP-Only, Secure, SameSite=Strict cookie.


* Token Revocation: Refresh tokens stored as SHA256 hashes in Redis key-value store, allowing instant token invalidation/session termination.

19. AUTHORIZATION & RBAC SPECIFICATION

`ADMIN` > `COMPANY_ADMIN` > `RECRUITER` > `CANDIDATE`

Permission Matrix Middleware Example:

```typescript
// Authorization guard ensuring user is associated with the resource's company
export const verifyCompanyAccess = async (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
  const { companyId } = req.params;
  if (req.user.role === 'ADMIN') return next();
  
  const membership = await prisma.companyMember.findUnique({
    where: { company_id_user_id: { company_id: companyId, user_id: req.user.id } }
  });
  
  if (!membership) throw new ForbiddenError("Access denied to target company resources");
  next();
};

```
